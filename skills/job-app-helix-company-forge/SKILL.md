# Job-App Helix Company Forge

## Identity

This skill turns a target company + role into a distinct, deployed, technically deep engineering artifact that proves hiring value.

It is not a template generator. It is a reusable process for discovering the unique project that should exist.

## Hard loop

Every major wave:

RESEARCH -> STUDY -> WORK -> VERIFY -> PRESERVE -> RESEARCH AGAIN

### Research
Use current primary sources, company engineering material, repos, docs, papers, product releases, role requirements, relevant library source/docs, benchmarks, incidents, and technical ecosystem signals.

### Study
Turn sources into working mastery:
- algorithms;
- protocols;
- architecture;
- data structures;
- failure modes;
- performance envelopes;
- language idioms;
- domain vocabulary;
- expert tradeoffs.

### Work
Implement the strongest coherent next capability in real code/state.

Never substitute research reports for implementation.

## Company discovery sequence

For each target:
1. identify company;
2. identify target role/team;
3. identify evidence-backed bottlenecks;
4. rank bottlenecks by impact x relevance x evidence x solvability x differentiation;
5. identify solution;
6. identify genuine innovation;
7. identify languages/stack based on the problem;
8. identify epistemology;
9. identify potential;
10. identify measurable impact;
11. derive architecture from this fingerprint.

## Anti-cookie-cutter

The workflow is reusable. The architecture is not preselected.

Derive:
COMPANY_FINGERPRINT = company + role + product + users + stack + culture + bottleneck + metric + domain + research frontier + integration surface + demonstration constraints

Reject generic architecture when deeper company-specific design is reachable.

Challenge chatbot-by-default, dashboard-by-default, RAG-by-default, agent-by-default, vector-DB-by-default, CRUD-by-default, microservices-by-default, and repeated portfolio folder structures.

Ask: If the company name changed, would most of this project still make equal sense? If yes, research and study deeper.

## Sequential intelligence

For complex design work, reason internally in dependency-aware sequence:
OBJECTIVE -> EVIDENCE -> CONSTRAINTS -> HYPOTHESES -> ROOT CAUSES -> ALTERNATIVES -> TRADEOFFS -> EXPERIMENT -> DECISION -> IMPLEMENTATION -> ADVERSARIAL REVIEW -> VERIFICATION -> NEXT FRONTIER

Persist consequential decisions, evidence, tests, and tradeoffs rather than private reasoning traces.

## Token saver

Preserve intelligence by shrinking repetitive context, not ambition.

Maintain compact durable state:
- company fingerprint;
- verified source map;
- bottleneck;
- thesis;
- architecture decisions;
- contracts;
- current wave;
- benchmark baseline/result;
- deployment;
- unresolved conflict;
- next frontier.

Give specialists focused context packets rather than full chat histories. Use delta-first resumption.

Never compact away exact requirements, source lineage, unresolved contradictions, interfaces/schemas, performance baselines, failure evidence, or important design rationale.

## Pro-Code Elite Humanized Engineering

Code must look intentionally engineered by a strong human practitioner.

Require:
- domain-driven names;
- clear architecture;
- useful abstractions;
- intentional algorithms/data structures;
- idiomatic language use;
- consequential WHY comments;
- actionable errors;
- failure recovery;
- observability;
- performance awareness;
- security;
- maintainability;
- integration tests;
- benchmarks where claims matter;
- reproducible execution.

Avoid sterile AI boilerplate, pattern worship, meaningless wrappers, comments that restate syntax, fake adapters, placeholder success, and TODO-as-delivery.

## Master practitioner review

For every major subsystem ask:
- What would a master in this field challenge?
- What is non-obvious and technically interesting?
- Are invariants explicit?
- What breaks at 10x?
- What does the profiler/benchmark show?
- What happens under partial failure?
- Is concurrency/backpressure correct where applicable?
- Is the implementation idiomatic?
- What tradeoff would an experienced engineer debate?
- What detail proves domain mastery rather than tutorial familiarity?

Strengthen weak answers before promotion.

## Atomic wave

RESEARCH -> STUDY -> UNDERSTAND EXISTING STATE -> DESIGN -> BUILD -> TEST -> INTEGRATE -> OBSERVE -> BENCHMARK/EVALUATE -> ADVERSARIAL REVIEW -> MASTER REVIEW -> VERIFY REAL PATH -> COMMIT/PRESERVE -> RECORD NEXT FRONTIER

Finish one coherent capability at a time.

## Mega-Skill composition

Before a major wave search Mega-Skills. Compose skills based on the company fingerprint, not a fixed bundle.

Useful classes include deep research, swarm orchestration, systems architecture, domain technology, agent evaluation, memory/context, autonomous repair, benchmarking/performance, security, frontend/UX, deployment, and observability.

If an important recurring capability is missing, build a reusable skill and preserve it in Mega-Skills.

## Continuous impressive recursion

After the system works and is deployed, improve it in waves:
correctness -> reliability -> security -> performance -> observability -> recovery -> developer experience -> product experience -> architectural clarity -> domain depth -> innovation -> company specificity -> demo quality.

Then ask:
- What is still ordinary?
- What would a master engineer find shallow?
- What breaks at scale?
- What experiment could invalidate our strongest assumption?
- What composition creates nonlinear leverage?
- What new bottleneck did this reveal?

Run another wave when the answer has material hiring-signal value.

## Completion standard

Do not stop at works.

Completion requires current company research, studied domain understanding, credible bottleneck, company-specific architecture, real implementation, strong tests, meaningful benchmark/evaluation, failure handling, observability, production deployment where feasible, deployed readback, recruiter explanation, hiring-manager thesis, master-engineer depth, and durable continuation state.
