# MCP Master Architect
System for structural orchestration of multiple MCP servers, defining hierarchy, data flow, and cross-server communication.

## 🏗️ The Unified Architecture
This architecture positions your various MCPs into a functional hierarchy:

### 1. The Brain (Orchestration Layer)
- **AI Cognitive Nexus**: The primary command center for team grouping and state management.
- **Mastermind Integration Orchestrator**: Synchronizes the 9 specialized agents.

### 2. The Muscle (Operational Layer)
- **Mastermind Agents**: Forensic Analyst, Legal Automation, Malware Detection, etc.
- **Repo Operator Protocol**: Universal project completion and deployment.

### 3. The Senses (Integration Layer)
- **Apple MCP**: Local system/app control (Mac/Termux).
- **StealthMole**: Dark web and threat intelligence.
- **Universal MCP Factory**: Dynamic integration of new APIs.

### 4. The Memory (Persistence Layer)
- **Supermemory**: Long-term episodic and semantic memory.
- **Cognitive Nexus Session Manager**: Multi-round dialogue persistence.

## 🛠️ Management Tools
- **Registry**: Centralized list of all active/available MCPs.
- **Activator**: Automated configuration of Cline/IDE settings.
- **Bridge**: Protocol for allowing one MCP to call another.

## When to Use

Use this skill when a task requires designing, reviewing, or reorganizing a system that contains multiple MCP servers, tool providers, memory layers, or cross-server routes.

## Operating Workflow

1. Inventory the MCP servers, transports, authentication boundaries, and durable stores that actually exist.
2. Classify each component by role: orchestration, operational execution, integration/sensing, or persistence.
3. Trace the required data and authority flow between components before adding bridges.
4. Define complete explicit contracts between servers: inputs, outputs, errors, identity, retry behavior, observability, security, and approval semantics. Use local narrowing only to isolate uncertainty; do not omit mission-relevant contract fields to make the bridge smaller.
5. Prefer direct provider-native integrations where they already satisfy the requirement; add a bridge wherever it creates justified capability, interoperability, resilience, or evidence value.
6. Validate the proposed topology against actual endpoints, schemas, and available tools.
7. Produce a complete architecture map plus the next executable implementation steps, dependencies, and verification gates.

## Verification

A valid result names the real components involved, shows how requests and state move between them, and distinguishes existing connections from proposed ones. Do not claim that a server, bridge, or credential path is live without observing it.
